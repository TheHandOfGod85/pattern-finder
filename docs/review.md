# A different model's review

## Who reviewed, and what

The review was run by the `diamond:code-reviewer` subagent: a fresh context, read-only tools, and a model
different from the implementers (Claude Opus). It was told the plan and the design are the requirements, and
that it may not fix anything.

The range was the whole Story, not the last phase: the plan's recorded start commit
`426a0501c8ff93c0c9176ee97b4c770a9c05b4dc` to the working tree, limited to the files the plan names. The
generated catalogue and the lockfile were shape-checked rather than read in full.

Before reviewing, the agent loaded the project rules and the global TypeScript and testing conventions, read
the plan and the design, and searched the existing code for the patterns it was comparing against.

## Strengths it recorded

- The pure-module split: `parse-year.ts`, `catalogue.ts`, `designs.ts` and `book.ts` each own one concern,
  take `unknown` input behind type guards, and carry their tests.
- Every plan scenario has a matching test, and the tests are not weaker than the scenarios. Boundary cases
  and missing data are covered.
- The V&A terms are structural: the credit is generated by the ingest and shown in the footer; images load
  from the museum's own addresses; the ingest waits one second after every request and writes nothing if a
  request fails.
- All API text goes through `textContent`; there is no `innerHTML` anywhere in Story code.
- The catalogue is validated at runtime before it reaches the renderer.
- The docs match the plan: the README has every command and the rebuild steps, and the deploy document has
  the exact commands and settings.

## The three Important findings, and what changed

### 1. A failed catalogue load produced a blank page

The design's error table says the page should show "The catalogue could not load. Run the ingest, then try
again." The page threw and left `#app` empty instead, so the reader saw nothing and the required V&A credit
disappeared too.

Fixed: the load is wrapped in a guard; the page renders the designed message, keeps the detailed error for
the console, and still shows the credit footer. Three page tests cover a rejected request, a non-OK response
and a malformed payload.

### 2. Pure logic sat in the page layer, and one branch had no test

`intersectYearRanges` and `buildPeriodStarts` were pure, non-trivial and unexported inside `main.ts`, which
the design defines as "read the catalogue and wire the DOM". The book-era and period intersection had no
direct test.

Fixed: both functions moved to `src/designs.ts` and are exported. Tests cover overlapping ranges, disjoint
ranges, period-only, book-only, both-null, and a catalogue with no dated designs.

### 3. Cards could only be opened with a mouse

The card was an `<article>` with a click listener and no keyboard path, so the app's primary action failed
WCAG 2.1.1.

Fixed: the card keeps its structure and gains `role="button"`, `tabindex="0"`, Enter/Space handling and a
focus outline. Two page tests open the detail view by keyboard. The existing click tests are untouched.

## The Minor findings, and the author's decisions

| # | Finding | Decision |
|---|---|---|
| 4 | The book status could claim "Showing designs from 1922 to 1952" while a selected period narrowed or emptied the grid | **Fixed.** The status is derived from the era and the current period; it reports the effective range, or says no designs fall in the chosen period |
| 5 | The four-week freshness rule is displayed but never warned on | **Declined.** The design asked for the date to be visible; the README documents the refresh |
| 6 | Every keystroke rebuilds all 1,854 cards | **Declined.** The live check was responsive |
| 7 | `isRecord` was duplicated in three modules | **Fixed.** One shared guard in `src/is-record.ts`, with its own tests |
| 8 | `passWithNoTests: true` would hide a broken test-discovery regression | **Fixed.** The setting was removed |
| 9 | The page had no `h1` | **Fixed.** A single page heading now precedes the controls |

One further edge was recorded rather than fixed: after a successful book lookup, a failed lookup leaves the
previous era filter applied while the status reports the failure. The author declined a change; the case has
no test cover and is not part of the demo flow.

## Re-review

The same reviewer re-ran the same range after the fix round. It confirmed all three Important findings
resolved with real branch coverage, the original scenario tests untouched, and no new Critical or Important
defect. Its verdict:

> **Ready to merge: Yes.** All three Important findings are resolved with real branch coverage, the original
> scenario tests are untouched, and `npm test` (85/85), `npx tsc --noEmit` and `npm run build` are green with
> relative asset paths. The six remaining Minors are optional polish, and no new Critical or Important
> defect was introduced.

The follow-up commit then took the suite to 95 tests.

## Limits of this review

- It is a different model, **same vendor**. It is not an independent vendor review, and the talk should say
  so.
- It reviewed the plan's files, not the whole repository.
- It did not test the live deployment or the third-party services (the V&A image server and Open Library)
  beyond what the orchestrator's browser check exercised.
- The generated catalogue is trusted as build output; the review checked its shape, not every record.
